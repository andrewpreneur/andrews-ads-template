# Running ads through GoHighLevel (Ad Publishing API)

There are **two ways** this system runs Meta ads. Pick one per campaign and stick with it.

| | **Path A: Meta Ads CLI / Graph API** | **Path B: GHL Ad Manager (this skill)** |
|---|---|---|
| Tools | `./run.sh`, `scripts/meta-kit.sh`, `ops/*.js` (Graph API v21, `ACCESS_TOKEN`) | HighLevel connector: `mcp__HighLevel__search_operations` → `describe_operation` → `execute_operation` |
| Auth | Meta system-user token in the environment | The GHL sub-account's Facebook integration (connected once in GHL → Ad Manager) |
| Best for | Full Meta control: any objective, existing creatives/post IDs, spend caps, read-only audits, the HQ snapshot, the daily check | Clients who live in GHL; ads built from GHL contacts/smart lists; instant forms that drop leads straight into the CRM; reporting that joins Meta spend with CRM-attributed contacts; Google and LinkedIn ads from the same place |
| Can't do (as of 2021-04-15 API) | CRM attribution (needs our own matching) | Campaign spending limits, reuse of an existing creative/post ID, objectives other than LEADS/TRAFFIC/ENGAGEMENT/SALES, Advantage+ shopping, editing campaigns it didn't create |

**Rule: one owner per campaign.** A campaign created in GHL is edited, paused and published through GHL. A campaign created with the CLI/Graph API (or in Ads Manager) is managed with Path A. GHL keeps its own copy of what it published (`unpublishedChanges`, `publishingStatus`); changing a GHL campaign directly in Meta makes the two disagree and the next GHL publish can overwrite it. Reading is fine from either side: Path A's read-only reports and the HQ snapshot cover every campaign in the ad account, GHL-made ones included.

**Which path for a given account:** record it in `CLAUDE.md` ("Ads path: A", "B" or "both: GHL for X, CLI for Y"). Default to A when it isn't recorded. Use B when the owner asks for it, or when the business runs on GHL and wants leads, audiences and reporting tied to its CRM.

All house rules apply on both paths: risk scale (0-7 do it, 8+ needs the owner's yes in their own words), the 4 creative checks, new things start PAUSED or as drafts, one change at a time then 3-5 days hands-off, judge on 7-day cost per real result, and log every change with a read-back in `reports/`.

## Two ways to call it
1. **HighLevel connector (preferred in Claude):** `mcp__HighLevel__search_operations` → `describe_operation` → `execute_operation`
   (see below). Auth is handled by the connector, bound to one sub-account.
2. **Direct HTTP (scripts, routines without the connector):** `https://services.leadconnectorhq.com` + the path, headers
   `Authorization: Bearer <token>` and `Version: v3`. Every Ad Publishing endpoint takes a **Sub-Account** token: an OAuth access
   token or a **Private Integration Token (PIT)** made in the sub-account (Settings → Private Integrations) with scopes
   `adPublishing.readonly` (the 50 GET endpoints) and `adPublishing.write` (the 46 write endpoints). Store a PIT as a network secret
   for `services.leadconnectorhq.com` (Claude's `request_credential`), never in a file or chat. `locationId` goes in the query/body
   where the reference marks it required.
- **Rate limits:** 100 requests / 10 s burst and 200,000 / 24 h per app (or per Private Integration) per sub-account; read the
  `X-RateLimit-*` headers and back off on 429.

## How the GHL connector works
1. **Find** the operation: `search_operations` with `domains: ["ad-publishing"]`. Full list: `references/operations.md`.
2. **Read the contract**: `describe_operation <id>`. Body fields change; never write from memory.
3. **Preview** writes with `execute_operation ... dryRun: true`, then run them with an `idempotencyKey` and a short `reason`.
4. The connection is bound to one GHL sub-account (location). Before the first write in a session, run `fb-get-integration` and check
   `status` is `connected` (not `expired`/`disconnected`), and `fbAdAccountId` and `fbDefaultPageId` are the account and Page you mean.
   `pricingModel` says who pays Meta: `connect_your_bm` (the business's own ad account and card) or `done_for_you` (billed through
   GHL). The response contains live Page access tokens (and `fb-create-integration` returns the user access token): **credentials,
   never write them to a file, report, commit or chat.**

## The build → publish → verify workflow (Facebook)
GHL builds campaigns as **local drafts** first. Nothing reaches Meta until you publish.

1. **Check the connection**: `fb-get-integration`, `fb-get-ad-accounts`, `fb-get-pages`, `fb-get-pixels` (pick the business's own pixel),
   `fb-get-instagram-accounts` (pageId).
2. **Campaign draft**: `fb-upsert-campaign` with `name`, `objective` (`OUTCOME_LEADS` | `OUTCOME_TRAFFIC` | `OUTCOME_ENGAGEMENT` |
   `OUTCOME_SALES`), `specialAdCategories` (`["NONE"]`; use `HOUSING` for real-estate listing ads, `EMPLOYMENT`, `CREDIT`,
   `FINANCIAL_PRODUCTS_SERVICES` where they apply). Budget lives on ad sets unless you set `isCampaignBudget: true` (then
   `budget {budgetType, amount}` + `bidStrategy` here and none on ad sets). `adsetBudgetSharing` and `isCampaignBudget` are exclusive.
   Name agent campaigns with the `[Claude]` prefix like on Path A.
3. **Ad set draft**: `fb-upsert-adset` with `campaignId` (required), `name`, `pageId`, `instagramActorId`, `audience`
   (`geoLocations` required; `ageMin/ageMax`, `genders`, `locales`, `interests`, `lookalike`, `retargeting`, `placementType: auto|manual`),
   `budget {budgetType: DAILY|LIFETIME, amount}`, and the conversion setup:
   - `conversionLocation`: LEADS → `website` | `on_ad` (instant form) | `website_and_lead_form`; SALES → `website` | `messaging`.
   - `customEventType` + `pixelId` when `conversionLocation` is `website`. LEADS allows `LEAD`, `COMPLETE_REGISTRATION`, `CONTACT`,
     `SCHEDULE`, `SUBMIT_APPLICATION`, `START_TRIAL`, `SUBSCRIBE`, `CONTENT_VIEW`, `SEARCH`, `FIND_LOCATION`; SALES allows `PURCHASE`,
     `INITIATED_CHECKOUT`, `ADD_TO_CART`, `ADD_PAYMENT_INFO`, `ADD_TO_WISHLIST`, `COMPLETE_REGISTRATION`, `CONTENT_VIEW`, `DONATE`,
     `SEARCH`, `START_TRIAL`, `SUBSCRIBE`. (Same Meta rule as Path A: Contact/Lead-type events need a LEADS campaign.)
   - `bidAmount` only with `LOWEST_COST_WITH_BID_CAP` or `COST_CAP`.
   - **Budget `amount` is in account currency (dollars), not cents.** `{"budgetType":"DAILY","amount":14}` = $14/day. The Graph API
     on Path A uses cents (`daily_budget: 1400`). Never copy a number between the two paths without converting; confirm with a
     read-back before publishing.
4. **Ad draft**: `fb-upsert-ad` with `campaignId`, `adsetId`, `name`, `mediaType: SINGLE|CAROUSEL`, `media: [{src, type: image|video, ...}]`
   (a public image/video URL; GHL uploads it), `primaryTexts: [{text}]`, `headlines: [{text}]`, `descriptions: [{text}]` (more than one
   = Meta text variations), `cta` (LEADS: `SIGN_UP`, `LEARN_MORE`, `APPLY_NOW`, `GET_QUOTE`, `GET_OFFER`, `DOWNLOAD`, `SUBSCRIBE`),
   and the destination: `destinationLink` (website, with UTMs), `destinationFormId` (instant form) or `conversationFormId`
   (Messenger form). Carousel cards take `media[].headline/description/link`.
5. **Review** with `fb-get-campaign` (campaignId): the whole draft with its ad sets and ads. Run the 4 creative checks on what's there.
6. **Publish = 8+.** `fb-publish-campaign` pushes the campaign to Meta and can start spending. Get the owner's yes, then publish, then
   poll `fb-get-campaign-publishing-progress` until done. The publish call returns the draft (`publishingStatus` still `DRAFT`, no
   Facebook ids); the ids arrive later.
7. **Verify on Meta** (not just GHL): read `fbCampaignId` / `fbAdSetId` / `fbAdId` from `fb-get-campaign`, then confirm status,
   budget and event with a Graph read (Path A, read-only) or `fb-get-entity type=INTEGRATION`. Check `fbError` on every object.
   Log ids and the read-back in `reports/YYYY-MM-DD-changes.md`.

### Changing live campaigns
- **Pause one losing ad** (0-7 if its ad set keeps other ads running): `fb-pause-ad`. Pause ad set / campaign (`fb-pause-adset`,
  `fb-pause-campaign`) is turning something off = 8+.
- **Resume / publish / duplicate a campaign or ad set, raise a budget** = 8+ (`fb-resume-*`, `fb-publish-campaign`,
  `fb-duplicate-campaign`, `fb-duplicate-adset`, `fb-upsert-adset` with a higher budget).
- **New ad in a live ad set** (0-7 after the 4 checks): `fb-upsert-ad` (or `fb-duplicate-ad` and edit), then `fb-publish-campaign`.
  Because that publish pushes every unpublished change in the campaign, check `fb-get-campaign` for other `unpublishedChanges` first.
- **Edits after publish** are saved as `unpublishedChanges` and only reach Meta on the next `fb-publish-campaign`.
- **Deletes** (`fb-delete-*`) are permanent: 8+, and prefer pausing.
- The same Meta locks apply: a published ad set's pixel/event/optimization can't change; ad creatives can't be edited (a new
  headline is a new ad).

## More traps (from the full contracts)
- **Nothing validates `cta`, `conversionLocation` or `customEventType` in GHL.** A wrong value saves fine in the draft and only fails
  at publish (Facebook rejects it). Check them against the lists above before publishing, then check `fbError` after.
- **SINGLE (image/video) ads read only the arrays:** `headlines` and `descriptions`. The singular `headline` is just the carousel
  fallback; `primaryText` is used only when `primaryTexts` is empty. Always send the arrays.
- Campaign `bidAmount` (only with `isCampaignBudget`/`adsetBudgetSharing`) is the default for every ad set; an ad set's own wins.
  `adsetBudgetSharing` lets Meta move up to 20% between sibling ad sets. Ad set schedule dates only work under a campaign budget.
- **Read-backs differ:** `fb-pause-ad`/`-adset` and `fb-resume-ad`/`-adset` return the whole parent campaign with ad sets nested;
  `fb-pause-campaign`/`fb-resume-campaign` return only `{success}`. Confirm with `fb-get-campaign` or a Meta read.
- **Pixels:** `fb-upsert-pixel` without `conversionPixelId` **creates a new pixel**: list with `fb-get-pixels` first and reuse the
  business's own. Renaming is the only update. `fb-get-pixels channel=IG` returns bare ids and ignores paging.
- **Two kinds of ids:** GHL's own ids (24-char, from upsert responses) for get/pause/publish calls; Meta numeric ids (`fbCampaignId`…)
  show up in entity and reporting calls. Check which one a call wants in the reference before sending.
- Publish-progress data only exists while publishing; if it's gone, read `fb-get-campaign`. `fb-get-pages` allows `limit` ≤ 50
  together with `fetchExisting`.
- **Google:** only `SEARCH` and `DEMAND_GEN` campaigns can be created; `maximumCpc` and reporting cost are in **micros**
  (1,000,000 = $1); reporting `groupBy` is `date`; `google-upsert-conversion` supports only `UPLOAD_CLICKS`; `google-get-keyword-ideas`
  is a POST that counts as a write (approval prompt) though it only reads.
- **LinkedIn:** `li-get-reporting-list` needs both `campaignGroupId` and `campaignId`; `li-update-ad-status` also takes `ARCHIVED`;
  `li-create-lead-form` publishes immediately (no drafts).

## Reporting
- `fb-get-reporting` (startDate, endDate, fields, groupBy, `type`): account totals. `fields` from `impressions, clicks, spend, cpc,
  conversions, results, cpm, reach, frequency, ctr`. **Traps:** `cpm`, `ctr` and `frequency` are *summed* in `totals` (recompute them
  from impressions/clicks/spend); `cost_per_result` and `cost_per_conversion` always read 0, so use `costPerResult` /
  `costPerConversion` or compute spend ÷ results.
- `fb-get-reporting-list` (listType `campaigns` | `adsets` | `ads`; adsets/ads need `campaignId`): per-object metrics. Objects with no
  insights come back as a zero row with fewer fields. `listType=none` fails (409).
- `fb-get-campaign-reporting` (published campaigns only): Meta insights **plus `leads` = contacts GHL attributed to the campaign**.
  `results.lead` (Meta's pixel leads) and `leads` (real CRM contacts) disagree. Judge on the CRM number, like on Path A
  ("count only ad-sourced results").
- `type`: `INTEGRATION` = everything in the Meta ad account; `AD_MANAGER` = only campaigns published from GHL (filtered to
  PAUSED/PUBLISHED). Use INTEGRATION for whole-account checks.
- `fb-get-entity` (entityType CAMPAIGN | ADSET | AD): status fields differ by type (campaigns have `status` + `effectiveStatus`, ad
  sets only `effectiveStatus`, ads only `status`). Missing `next` = end of results. Pause by each object's own status, as on Path A.

## Audiences from the CRM
- `fb-get-custom-audiences` / `fb-get-custom-audience-by-id`: list and inspect (lookalike spec, website rule, customer-list source).
- `fb-add-custom-audience-member` / `fb-remove-custom-audience-member`: one GHL contact (hashed by GHL before sending).
- `fb-batch-update-audience-members`: bulk add/remove from a CSV or GHL smart lists (queued; the reply only means "accepted").
  **`operationType: REPLACE` swaps out the whole membership**: never use it without the owner's OK. One of `csvPath`/`smartlistIds` is required.
- **No endpoint creates a custom audience** (or lookalike). Create it in Meta (Path A or Ads Manager) or the GHL UI, then manage members here.
  `fb-update-custom-audience` only renames/re-describes. `fb-get-custom-audiences` needs `adAccountId` and `type` (`custom`|`lookalike`|`all`).
- Use for retargeting (registrants, no-shows, trial users), exclusions (current customers) and lookalike seeds. Audience
  edits are 0-7. Targeting a live ad set at a new audience is a targeting change = 8+.
- Customer data stays inside GHL and Meta. Never copy members into the repo or a report: totals only.

## Instant forms and conversation forms
- `fb-get-page-lead-forms`, `fb-get-lead-form`, `fb-create-page-lead-form` (`isDraft: true` saves locally). Always required: `type`
  (`MORE_VOLUME` | `HIGHER_INTENT`). To publish: ≥1 question, `privacyPolicyLink`, and a full `thankYouPage` {title, body, buttonText,
  buttonType}; pass `draftFormId` to clean up the draft. Drafts come back under `_id` with a `draft_` prefix; a published form read
  back has no `status`/`createdTime`/`pageId`. Leads land in GHL as contacts.
- `fb-get-conversation-forms`, `fb-create-conversation-form`: Messenger lead forms (`conversationFormId` on the ad).
- A new published form that customers see is part of a launch: get the owner's OK on the questions and thank-you page copy.

## Google and LinkedIn
Same connector, same pattern: `google-upsert-campaign` (full structure) → `google-publish-ad` → `google-get-publishing-progress`;
reporting via `google-get-reporting(-list)`; keyword ideas via `google-get-keyword-ideas`. LinkedIn: `li-upsert-campaign-group`,
`li-update-ad-status`, `li-get-reporting-list`. Every operation is listed in `references/operations.md`; read its contract with
`describe_operation` before using it.

## Daily routine on Path B
1. `fb-get-integration` (still connected? right account?).
2. `fb-get-reporting-list type=INTEGRATION listType=campaigns` for the last 7 days, then `adsets`/`ads` for each live campaign.
3. `fb-get-campaign-reporting` for GHL-published campaigns, to get CRM-attributed leads.
4. Judge on 7-day cost per real result against the tiers; make 0-7 moves (`fb-pause-ad`, new checked ad + publish); list 8+ items.
5. Write the report and refresh the HQ page as in `CLAUDE.md`. The HQ snapshot (`ops/copilot-snapshot.js`) still reads Meta directly
   and covers GHL-made campaigns too.
